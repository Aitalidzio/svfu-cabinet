# Архитектурные решения

Короткий журнал решений: что выбрали, почему и что отбросили. Новое решение дописывается в конец.

## 1. Next.js как единое full-stack приложение — 08.11.2026

**Решение.** Интерфейс и сервер живут в одном проекте на Next.js 16 (App Router).

**Почему.**
- Один репозиторий и один деплой. Для команды из двух человек за две недели это заметно проще, чем отдельный фронтенд и бэкенд.
- Серверный рендеринг: страница приходит уже с данными. На слабом телефоне и мобильном интернете это быстрее, чем SPA, которая сначала грузит JS, а потом данные.
- Server Actions и Data Access Layer держат доступ к данным на сервере. Это напрямую закрывает требование «студент видит только свои данные».
- Масштабирование: сервер Next.js не хранит состояние, поэтому под нагрузкой можно поднять несколько копий за балансировщиком с общей базой.

**Отбросили.** Отдельный бэкенд на FastAPI или Express (два проекта и больше работы); конструкторы без кода (не проходят требование «ключи не в браузере» и плохо масштабируются).

## 2. PostgreSQL + Drizzle ORM, локально PGlite — 08.11.2026 (подтверждено на этапе 4, 13.11.2026)

**Решение.** Основная база — PostgreSQL. Работаем с ней через Drizzle ORM. На компьютере разработчика вместо отдельного сервера используется PGlite (Postgres, скомпилированный в WebAssembly и работающий внутри Node.js).

**Почему.**
- PostgreSQL — стандарт для учётных систем, он легко выдерживает тысячи студентов.
- Drizzle описывает схему на TypeScript и делает типобезопасные запросы, а SQL в нём остаётся понятным.
- PGlite избавляет от установки Postgres или Docker на Windows-ноутбук: `npm run dev` сразу работает.

**Отбросили.** SQLite (хуже с масштабированием и параллельной записью, жюри может придраться); хранение в `localStorage` (не настоящая база и небезопасно).

## 3. Собственный вход на сессиях в БД — 08.11.2026

**Решение.** Логин и пароль. Пароль хешируется через scrypt из `node:crypto`. После входа создаётся случайный токен: в cookie (httpOnly, Secure, SameSite=Lax) лежит сам токен, в БД — его хеш.

**Почему.**
- Сессию можно отозвать на сервере (кнопка «Выйти на всех устройствах»), с JWT так не получится.
- scrypt встроен в Node.js: нет нативных зависимостей, которые ломаются на Windows или на сервере.
- Схема простая, её легко объяснить жюри «простыми словами».

## 5. Коммиты делает человек — 08.11.2026

ИИ не делает коммиты и пуши. Капитан команды сам проверяет каждое изменение и коммитит его небольшими порциями.
Так история репозитория показывает, что каждое изменение проверено человеком.

## 6. Три языка через путь в адресе: `/ru`, `/sah`, `/en` — 13.11.2026

**Решение.** Все страницы лежат внутри `src/app/[lang]/`. Язык виден в адресе: `/ru/schedule`, `/sah/schedule`, `/en/schedule`. Тексты интерфейса берутся из словарей (`src/i18n/dictionaries/*.json`), а язык в коде читается через `next/root-params`.

**Почему.**
- Так рекомендует документация Next.js 16.4 (`01-app/02-guides/internationalization.md`).
- Для каждого языка заранее собирается своя быстрая «оболочка» страницы. Если хранить язык в cookie, все страницы пришлось бы рендерить на каждый запрос.
- Ссылкой можно поделиться сразу с нужным языком.
- Двухбуквенного кода у якутского языка нет, поэтому используем код `sah` по стандарту ISO 639.

**Отбросили.** Язык в cookie (медленнее с `cacheComponents`); готовые библиотеки вроде `next-intl` (для трёх словарей встроенного механизма хватает, а лишняя зависимость может не поддерживать Next.js 16.4).

## 7. Основа дизайна: шрифт Onest, палитра «полярная ночь и сияние», навигация — 13.11.2026

**Шрифт — Onest.** Главное требование: поддержка якутских букв Ҕ ҕ Ҥ ҥ Ө ө Һ һ Ү ү. Мы не стали верить описаниям шрифтов, а проверили 22 шрифта Google Fonts скриптом на fontTools: он скачивает файлы шрифтов и читает их таблицу символов (cmap).

| Результат | Шрифты |
|---|---|
| Все якутские буквы есть | Inter, Onest, Golos Text, Montserrat, Rubik, Nunito, PT Sans, Geologica, Commissioner, Raleway, Mulish, Exo 2, IBM Plex Sans, Noto Sans, Comfortaa |
| Нет Ҕ и Ҥ | Manrope, Roboto Flex, Source Sans 3 |
| Нет ни одной якутской буквы | Unbounded, Jost, Wix Madefor Text, Wix Madefor Display |

Скрипт лежит в `tools/check_sakha_fonts.py`. Из подходящих выбрали Onest: современный гротеск, хорошо читается на телефоне, один файл с переменной жирностью. Подключаем с набором `cyrillic-ext`, где и лежат якутские буквы. В браузере проверили, что этот набор действительно загружается на странице `/sah`.

**Палитра.** Глубокий синий цвет «полярной ночи» и градиент «северного сияния» (синий → фиолетовый → бирюзовый) для главного блока и логотипа. Отдельные цвета для статусов: успех, предупреждение (переносы), опасность (не хватает баллов). Есть светлая и тёмная тема, она выбирается по настройке системы. Скрипт `tools/check_contrast.py` проверил контраст 16 пар «текст / фон» в каждой теме: все ≥ 4.5 : 1, требование WCAG AA выполнено (худший результат 4.71). Белый текст на всех трёх цветах градиента — от 4.89 и выше. Цвета заданы токенами в `src/app/globals.css`, в коде используются только они.

**Навигация.** На телефоне — нижняя панель с 5 вкладками (Сегодня, Расписание, Баллы, Заявки, Профиль) и колокольчик уведомлений сверху: всё основное под большим пальцем. На компьютере (от 1024 px) — боковая панель со всеми разделами. Зона нажатия у всех пунктов ≥ 44 px.

**Логотип (временный).** Гранёный кристалл как отсылка к якутским алмазам и «граням знаний». Нарисован с нуля и не повторяет официальный логотип СВФУ. Окончательный логотип придумаем вместе с названием.

**Отбросили.** Manrope и Unbounded: популярны в «дизайнерских» интерфейсах, но не поддерживают якутский язык. Готовую библиотеку компонентов (shadcn/ui и подобные) не взяли: для нескольких простых компонентов она лишняя, а свои токены дают цельный стиль.

## 8. Вход и проверка доступа: два слоя, сессии в базе — 13.11.2026

**Решение.**
- **Drizzle ORM 0.45.4** — последняя стабильная версия. Ветка 1.0 пока в стадии release candidate, на ней прототип для жюри не строим.
- **Пароли — scrypt** из `node:crypto` (параметры N = 2¹⁵, r = 8, p = 1), у каждого пароля своя соль. **Сессия** — случайный 256-битный токен: в cookie (httpOnly, Secure, SameSite=Lax) лежит сам токен, в базе — только его SHA-256.
- **Два слоя проверки.** `proxy.ts` смотрит только, есть ли cookie сессии, и не ходит в базу, как рекомендует документация Next.js. Настоящая проверка — в слое доступа к данным (`src/server/dal`) перед каждым чтением данных и в каждом Server Action.
- **Ограничение попыток** хранится в таблице `login_attempts`: 5 неудач на логин и 20 на IP за 15 минут. Лимит по IP действует, только если IP известен (иначе один злоумышленник заблокировал бы всех).
- **Демо-пароль не хранится в коде.** Скрипт `db:setup` берёт его из `.env.local` или генерирует случайный.

**Почему не JWT и не готовая библиотека (Auth.js, Lucia).** Сессию в базе можно отозвать, отсюда работает кнопка «Выйти на всех устройствах». Своя реализация занимает около 150 строк, и её легко объяснить жюри. Готовые библиотеки добавляют зависимости, которые могут ещё не поддерживать Next.js 16.4.

**Особенность Next.js 16.4 + PGlite.** PGlite выполняет SQL прямо в процессе, а функция `now()` в нём читает часы JavaScript. Next.js с `cacheComponents` принял это за `Date.now()` во время пререндеринга. По документации (функция `io()`, появилась в 16.3) перед запросом к базе ставим `await io()`. Это сделано в одном месте, в `db()`.

Подробно и простыми словами — [security.md](security.md).

## 9. Расписание: регулярные пары + изменения на даты, время по Якутску — 13.11.2026

**Решение.**
- Регулярные пары хранятся по дням недели (`lessons`), изменения — отдельными записями на конкретную дату (`lesson_changes`): отмена, перенос (на другой день или пару), изменение (другая аудитория или преподаватель). День собирается так: «пары этого дня недели» + «изменения на эту дату». Отсюда видно «было → стало», а перенос показан в обоих днях: «Перенесена на…» и «Перенесена с…».
- Поддерживается чередование недель (`week_parity`: каждую / нечётную / чётную). Номер недели считается от начала семестра.
- «Сегодня» и «Идёт сейчас» считаются по времени Якутска (`Asia/Yakutsk`), а не по часовому поясу сервера: хостинг может оказаться в Москве, и тогда в 06:00 по Москве в Якутске уже полдень.
- Расписание любой группы видно любому вошедшему пользователю: это не персональные данные, как расписание на стенде. По умолчанию открывается своя группа. Без входа расписание недоступно.
- Демо-изменения повторяются трёхнедельным циклом со 2 ноября по середину декабря, чтобы на любой неделе, когда жюри откроет сайт, были переносы и замены.

**Почему не хранить каждое занятие отдельной датой.** Тогда при изменении регулярного расписания пришлось бы переписывать сотни строк, а «было → стало» вычислялось бы сравнением. Модель «правило + исключения» — стандартная для расписаний (так устроены календари) и проще для сотрудника деканата: перенос — это одна запись.

## 10. Успеваемость: правила БРС в одном модуле с тестами, тревога с учётом оставшихся баллов — 13.11.2026

**Решение.**
- Все пороги БРС (зачёт 60; «3/4/5» — 55/65/85; экзамен: семестр до 70, допуск 45, автомат 65, экзамен до 30) живут только в `src/lib/brs.ts`. Это чистые функции без базы и интерфейса, покрытые 24 тестами (`npm test`, ещё 7 — у календаря). Подсказки на странице строятся из результата `assess()`, а не считаются в разметке.
- Данные: дисциплина группы в семестре (`disciplines`) → запланированные контрольные (`assessments`) → баллы студента (`assessment_results`). Итоги прошлых семестров — `record_book`. Из этого видно и «сколько набрано», и «сколько ещё можно набрать», и «из чего баллы».
- **Уровень тревоги** зависит от доли оставшихся баллов, которую нужно набрать (функция `effort`). Первая версия правил считала текущую оценку «как есть», и в середине семестра почти у всех вышла бы «тройка» и «стипендия под угрозой». Ошибку заметили на этапе подготовки демо-данных, до того, как она попала в интерфейс.
- Запросы к баллам и зачётке фильтруются по id пользователя из сессии. Параметра, через который можно запросить чужие баллы, нет вообще.
- Слова после чисел склоняются через `Intl.PluralRules`: в русском три формы (балл, балла, баллов), в английском две, в якутском одна («баал» после числа не меняется).

**Отбросили.** Отдельную страницу дисциплины `/grades/[id]`: разбивка по контрольным раскрывается прямо в карточке, а без id в адресе нет и поверхности для подмены чужого id.

## 11. Заявки: каталог и валидация в одном модуле, история статусов, чужой id → 404 — 13.11.2026

**Решение.**
- Типы справок/заявлений, поля форм, сроки в рабочих днях и проверка ввода живут в `src/lib/requests.ts` (как БРС для оценок). Server Action и форма читают один каталог; модуль покрыт тестами (выходные не считаются в срок готовности, лишние поля формы отбрасываются).
- В базе: `requests` + `request_events` (каждое изменение статуса — строка истории). Статусы: подана → в работе → готова → выдана, либо отклонена / отменена студентом, пока ещё «подана».
- Студент видит и меняет только свои заявки. `getMyRequest(id)` всегда фильтрует по владельцу из сессии; чужой или несуществующий id даёт одну и ту же 404 внутри кабинета (`not-found.tsx`), чтобы не раскрывать, что заявка есть.
- Лимит: не больше 10 заявок в сутки на студента (по времени Якутска) — защита от случайного или злонамеренного потока.
- Кабинет сотрудника и уведомления о смене статуса — следующие этапы; демо-заявки уже лежат в разных статусах, чтобы жюри увидело историю без сотрудника.

**Отбросили.** Трекер «как у доставки» (решение команды в product.md). Отдельную таблицу под каждый тип справки — поля различаются слабо, хватает `details` (jsonb) с проверкой по каталогу.

## 12. Уведомления: одна таблица, фильтры по категории, тексты событий на русском — 13.11.2026

**Решение.**
- Таблица `notifications`: получатель из сессии, категория (`deanery` / `schedule` / `requests`), заголовок и текст, необязательная ссылка без языка (`/requests/1`), время прочтения.
- Лента студента с фильтрами из адреса (`?category=`). «Прочитать» и «Прочитать все» — Server Actions; чужой id ничего не меняет. Колокольчик в шапке и пункт в боковой панели показывают число непрочитанных.
- Тексты объявлений и сообщений о событиях хранятся по-русски (как названия дисциплин — product.md «Языки»). Подписи фильтров и кнопок — в словарях трёх языков.
- Создание уведомлений — серверная функция `createNotifications` (сейчас сид; позже — смена статуса заявки, перенос пары, объявление сотрудника). Клиент не передаёт `userId`.

**Отбросили.** Отдельные таблицы под каждый тип события; push/PWA (идея «на потом»). Кабинет сотрудника, который сам шлёт уведомления, — следующий этап; демо уже показывает ленту с разных категорий.

## 13. Экран «Сегодня»: сборка из существующих DAL, без новых таблиц — 13.11.2026

**Решение.**
- Главный экран не хранит свои данные: `getTodayOverview()` вызывает расписание, баллы, заявки и уведомления. Новых таблиц нет.
- Порядок блоков: изменения на сегодня/завтра (если есть) → текущая/следующая пара → дисциплины, где «горит» → активные заявки → непрочитанные уведомления → ближайшие дедлайны (контрольные, сессия, срок заявки).
- Сотруднику — приветствие, пара группы института и пояснение; персональные баллы и заявки не показываем.

**Отбросили.** Дублировать логику БРС или «Идёт сейчас» в разметке — только через `brs.ts` / `schedule` DAL.
