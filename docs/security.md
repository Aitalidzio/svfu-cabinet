# Как устроены вход, хранение данных и защита

Простыми словами — для отчёта жюри. Подробности в коде: `src/server/`.

## Где хранятся данные

- Все данные лежат в базе **PostgreSQL** на сервере. В браузере студента нет ничего, кроме cookie входа.
- На компьютере разработчика вместо отдельного сервера базы работает **PGlite**: тот же PostgreSQL, только запущенный внутри приложения. Поэтому проект запускается без установки базы данных.
- Все люди, группы и номера зачёток в базе **вымышленные**.

## Как хранятся пароли

- Пароль **никогда не сохраняется** в открытом виде. В базу записывается только его «отпечаток» (хеш), посчитанный алгоритмом **scrypt**.
- scrypt специально медленный и требует много памяти: одна проверка пароля занимает около 32 МБ и десятки миллисекунд. Подбирать пароли по украденной базе очень дорого.
- У каждого пароля своя случайная **соль**. Даже если у двух студентов одинаковый пароль, в базе их хеши разные. *(На этапе 4 ИИ сначала допустил здесь ошибку: проверка базы её показала, и ошибку исправили.)*
- При сравнении хешей используется сравнение «за постоянное время». По скорости ответа нельзя понять, сколько символов совпало.

## Как работает вход

1. Студент вводит логин и пароль. Форма отправляется на сервер (Server Action), в браузере пароль не проверяется.
2. Сервер ищет пользователя и сверяет хеш пароля.
3. Если всё верно, сервер создаёт **сессию**: случайный токен длиной 256 бит.
   - Токен уходит в браузер в cookie с флагами **httpOnly** (JavaScript на странице не может его прочитать), **Secure** (передаётся только по HTTPS) и **SameSite=Lax** (не отправляется с чужих сайтов).
   - В базе хранится не сам токен, а его хеш SHA-256. Даже утечка таблицы сессий не позволит войти под чужим именем.
4. Сессия живёт 7 дней. Кнопка «Выйти» удаляет сессию, а «Выйти на всех устройствах» удаляет все сессии пользователя сразу.

## Защита от подбора пароля

- На неверный логин и на неверный пароль показывается **одно и то же сообщение**, и время ответа одинаковое: для несуществующего логина сервер всё равно считает хеш. Так нельзя выяснить, какие логины существуют.
- После **5 неудачных попыток за 15 минут** вход под этим логином временно блокируется. С одного IP-адреса допускается не больше 20 неудач.
- Счётчик попыток хранится в базе, а не в памяти, поэтому работает, даже если запущено несколько копий сайта.

## Студент видит только свои данные

Проверка идёт в два слоя:

1. **Быстрая проверка на входе** (`src/proxy.ts`). Если у браузера нет cookie сессии, любая страница кабинета перенаправляет на вход. Эта проверка не обращается к базе: она только отсекает явно не вошедших.
2. **Настоящая проверка у данных** (`src/server/dal/`, «слой доступа к данным»). Любые данные читаются только через функции, которые сами берут пользователя из сессии и проверяют её в базе. Эти функции **не принимают id пользователя извне**: подставить чужой id в адрес или в запрос просто некуда. Каждое действие (Server Action) заново проверяет сессию и не доверяет тому, что кнопка была показана.

В интерфейс уходят только нужные поля: имя, группа, курс. Хеш пароля и служебные данные в браузер не попадают.

Заявка по адресу `/requests/[id]` открывается только если она принадлежит текущему студенту. Чужой или несуществующий номер даёт одну и ту же страницу 404 — по ответу нельзя понять, есть ли такая заявка у кого-то другого. Отмена заявки в Server Action снова проверяет владельца и статус: чужой id или заявка уже «в работе» просто ничего не меняют.

Уведомления читаются только для текущего пользователя из сессии. Отметить прочитанным чужое уведомление нельзя: в UPDATE всегда есть условие «владелец = я». Ссылка из уведомления — только путь внутри кабинета (без `//`), чтобы нельзя было увести на чужой сайт.

Сотрудник деканата видит заявки только студентов **своего института**. Заявка другого института или подставленный id дают ту же 404. Смена статуса, объявление и перенос пары заново проверяют роль и институт в Server Action; список получателей уведомлений строится на сервере, а не приходит из формы.

## Секреты

- Пароль базы данных и пароль демо-аккаунтов лежат только в файле `.env.local` на компьютере и в переменных окружения на сервере.
- `.env.local` исключён из git (`.gitignore`), в репозитории есть только пустой шаблон `.env.example`.
- В коде и в браузере нет ни одного ключа.

## Как мы это проверили (этап 4)

| Проверка | Результат |
|---|---|
| Открыть `/ru/profile` без входа | перенаправление на страницу входа |
| Неверный пароль / несуществующий логин | одинаковое сообщение «Неверный логин или пароль» |
| 6 неудачных попыток подряд | после 5-й вход блокируется на 15 минут |
| Вход двумя разными студентами | каждый видит только свой профиль |
| `document.cookie` в браузере после входа | cookie сессии не видна JavaScript (httpOnly) |
| Таблица `users` в базе | только хеши `scrypt$…`, у каждого своя соль, открытых паролей 0 |
| Таблица `sessions` после «Выйти на всех устройствах» | сессий пользователя не осталось |
